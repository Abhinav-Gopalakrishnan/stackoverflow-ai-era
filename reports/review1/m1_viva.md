# Member 1: Viva Questions for Data Collection & Sampling (M1-VIVA)

Five likely examiner viva questions, with concise, rigorous model answers based on the code, data collection log, and dataset documentation.

| # | Likely Question | Model Answer |
|:---|:---|:---|
| **1** | **Why did you use stratified day-level sampling instead of simple random sampling of questions? How are sampling weights computed?** | Uniform random sampling of questions across an 8-year API with 4M+ records is impossible without downloading the entire index. Stratified sampling by day (1 random weekday + 1 random weekend day per tag-month pre-2025, seed 42) avoids diurnal/day-of-week bias and enables exact inverse-probability weighting: $w = \frac{\text{days of type in month}}{\text{days sampled}}$ (e.g. 21 weekdays / 1 sampled = weight 21.0). In 2025+, because site-wide volume dropped ~90%, we switched to 100% exhaustive census collection ($w = 1.0$) to eliminate sampling noise in the post-AI evaluation period. |
| **2** | **How did you detect and fix the Stack Exchange API pagination bug? How many records were recovered?** | On high-volume tag-days, the Stack Exchange API returned `has_more=False` on page 1 even though subsequent pages contained unreturned questions. We detected this when comparing collected question counts against `filter=total` population totals. We resolved this in `src/collect.py` and `src/collect_questions.py` by always probing `page + 1` past `has_more=False` until a genuinely empty response ($0\text{ items}$) is received. This recovered **3,222 missing questions for `reactjs`** and **393 for `docker`**. |
| **3** | **Why does your Docker 2025 collected question count differ from `filter=total`? Is this a data collection error?** | No, this is an inherent platform property of the Stack Exchange API. The `filter=total` endpoint counts all questions created in that timestamp window, including questions that were subsequently deleted or locked by moderators. However, the paged `/questions` endpoint strictly omits deleted and locked posts from search results. This gap (6% to 19% in Docker 2025) is fully documented in `docs/dataset_documentation.md` and `docs/sampling_limitations.md`. |
| **4** | **How do your collected weekly counts compare with official Stack Exchange Data Explorer (SEDE) numbers? Why do published figures disagree slightly?** | We cross-validated 400 weekly counts across 13 tags against SEDE T-SQL queries. Across the entire 8-year window, our weekly API population sums match monthly population counts within **$\le 0.01\%$** (e.g. difference of only -102 questions out of 1.15M for Python). Published sources disagree slightly ($<0.5\%$) due to two reasons: (1) SEDE database dumps update weekly on Sunday mornings, capturing questions deleted in the interim, and (2) 52 7-day weeks ($364\text{ days}$) vs 365-day calendar years cause the 365th day to roll across annual boundaries. |
| **5** | **How do you ensure user privacy and compliance with Stack Exchange's license? Did you leak any raw user IDs or API keys?** | All user-contributed content is licensed under CC BY-SA 4.0. We ensure complete privacy by: (1) hashing raw user IDs immediately upon collection with salted SHA-256 (`hashlib.sha256(f"{salt}{uid}".encode())`) and storing only `owner_user_hash`, (2) masking batched ID parameters in committed logs (`users/{ids}`), (3) applying minimal API filters (`base="none"`) that exclude display names and profile URLs, and (4) storing API keys and `HASH_SALT` strictly in untracked `.env`. Automated regex and prefix scans verified **0 raw user IDs and 0 API key leaks** across all logs, notebooks, and git history. |
