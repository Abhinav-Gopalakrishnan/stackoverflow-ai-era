## Part 1: Core Architectural & Conceptual Viva Questions

### Q1: Why did you choose Streamlit, and why is `@st.cache_data` critical?
**Answer:**
Streamlit was selected because it enables rapid, pythonic construction of interactive, data-dense applications with native support for Plotly charts, markdown formatting, and tabular data without requiring frontend JavaScript scaffolding. 

However, Streamlit re-executes the entire script top-to-bottom on every user interaction (e.g., changing a dropdown or dragging a slider). Without caching, every interaction would trigger disk I/O, parsing 27 CSV files from disk repeatedly, introducing severe UI latency (1–2 seconds per click). 

`@st.cache_data` decorates our `load_data(filename)` function in `dashboard/common.py`. It memoizes the resulting pandas DataFrame in memory based on the filename key. Subsequent page visits or filter adjustments retrieve the in-memory object in under a millisecond, guaranteeing sub-second response times across the entire application.

### Q2: How does the sidebar share filter state across multiple pages?
**Answer:**
Streamlit multi-page applications maintain an isolated script context for each page in `dashboard/pages/`. To ensure seamless navigation—for example, selecting the `python` tag on Page 2 and having Page 3 (Forecasts) and Page 6 (Recommendations) immediately focus on `python`—we manage state centrally using `st.session_state`.

In `dashboard/common.py`, the `render_sidebar()` function initializes session keys if not already present:
- `st.session_state["selected_tags"] = ["ALL"]`
- `st.session_state["period"] = "all"`
- `st.session_state["show_events"] = True`
- `st.session_state["log_scale"] = False`

When a user modifies the multiselect widget or radio buttons in the sidebar on any page, the new value is immediately written back to `st.session_state`. When the user navigates to another page, that page calls `render_sidebar()` or reads `st.session_state["selected_tags"]`, maintaining unbroken user context across the entire analytical workflow.

### Q3: How do the export script (`src/export_dashboard_data.py`) and schema test (`tests/test_export_dashboard_data.py`) protect the application?
**Answer:**
In a multi-member research team, upstream modeling scripts are constantly refactored, and CSV outputs may change column names, index structures, or data formats. Connecting a live web application directly to raw modeling output folders creates brittle dependencies where an unexpected column rename crashes the UI during a live demonstration.

Our export architecture establishes a strict **protective contract**:
1. `src/export_dashboard_data.py` defines an explicit specification dictionary (`EXPORT_SPECS`) declaring the exact files, expected source paths, and mandatory columns required by each dashboard chart.
2. The export script verifies that every source file exists and contains the required schema before copying and slimming the file into `dashboard/data/`.
3. `tests/test_export_dashboard_data.py` runs 30 automated unit tests verifying that all 27 files exist, are non-empty, match the exact column set, contain zero forbidden or PII fields, and keep the total bundle size under 50 MB.
This decoupling guarantees that the dashboard will never crash due to upstream format modifications.

### Q4: Why are questions referenced by "titles only" and how does that relate to licensing?
**Answer:**
Stack Overflow user contributions (questions, answers, code blocks) are licensed under **Creative Commons Attribution-ShareAlike 4.0 International (CC BY-SA 4.0)**. 

To maintain strict compliance and user privacy:
1. We store and serve **zero question bodies, code snippets, or user account information** within the dashboard repository or deployment bundle.
2. We display only the **post title**, accompanied by an explicit attribution link formatted directly to canonical URLs: `https://stackoverflow.com/q/<question_id>`.
3. Clicking any topic example immediately directs the evaluator to the original Stack Overflow source page, honoring attribution without redistributing copyrighted user text.
4. The dashboard sidebar incorporates an explicit "About Data & Licence" expander detailing data provenance (BigQuery public datasets and Stack Exchange API 2.3) and CC BY-SA terms.

### Q5: How do the dashboard and the master notebook (`review2_main.ipynb`) read the exact same data?
**Answer:**
Both the dashboard and the master notebook adhere to our team's strict **"single source of truth"** principle:
- All underlying analytical figures are generated by the core modeling scripts and stored in `reports/review2/ts/` and `reports/review2/text/`.
- `notebooks/review2_main.ipynb` directly loads these authoritative CSV files to render summary tables and diagnostic plots in Sections 1 through 5.
- The dashboard reads from `dashboard/data/`, which is a byte-for-byte validated mirror produced by `src/export_dashboard_data.py`.
Because both deliverables derive from identical underlying files, there is zero discrepancy between the numbers presented in the notebook and the numbers displayed in the interactive UI.

### Q7: Why are `low_sample` months greyed out on the dashboard charts?
**Answer:**
In our data collection strategy, months prior to 2025 were sampled using stratified random sampling (2 days per month: 1 weekday, 1 weekend day), whereas 2025 onwards was collected as a full census. For niche technologies or early calendar years, a sampled month might contain fewer than 30 total question records.

Computing percentage rates (such as resolution rate or sentiment polarity shares) on a sample size under 30 introduces high binomial variance; a shift of just one or two posts could swing a percentage by 10–15 points, creating misleading visual spikes. 

We explicitly flag any month where $N < 30$ with `low_sample = True`. On dashboard charts (such as Page 5 Tone shares), these points are rendered with reduced opacity (25%) or grey open markers, and our dynamic chart title algorithms programmatically exclude them from empirical conclusions.

### Q8: What does the work plan's "one source for every number" rule mean here?
**Answer:**
The "one source for every number" rule dictates that **no metric, percentage, slope estimate, or test statistic may be hard-coded or typed by hand** into markdown text, chart titles, or slide decks. 

Every single figure must be programmatically read from an authoritative CSV/JSON artifact in `reports/review2/`:
- ITS slope changes come strictly from `its_results.csv` (e.g., Python slope: -2.34%/wk).
- 26-week projections and half-life estimates come strictly from `tag_classes.csv` and `forecasts_26w.csv`.
- Structural complexity changes come strictly from `complexity_prepost.csv` (e.g., Prose median +13 words, 95% CI [12, 13]).
- Frustration rates come strictly from `tone_prepost.csv` (-0.2 pp change).
In our dashboard code, all chart titles are dynamically assembled via f-strings reading directly from the loaded dataframes (e.g., `f"ITS Regression for {selected_tag}: {slp_chg:+.1f}% slope change..."`), preventing human transcription error.

## Part 2: Code Walk-Through

### Walk-Through: `dashboard/common.py`

| Component / Function | Purpose & Implementation Details |
|---|---|
| `DATA_DIR` | Resolves absolute path to `dashboard/data/` using `Path(__file__).resolve().parent / "data"`, ensuring file resolution succeeds regardless of working directory. |
| `TAG_COLORS` | Fixed dictionary mapping all 13 study tags plus `ALL` to academic, colorblind-friendly hex palettes (e.g., `#1D4E89` for ALL, `#3572A5` for Python, `#DC2626` for OpenAI-API). |
| `ALL_TAGS` | Ordered list of 14 tag scopes used across dropdowns and selectors. |
| `load_data(filename)` | Wrapped in `@st.cache_data`. Reads CSV from `DATA_DIR / filename`, raising `FileNotFoundError` if missing. Caches DataFrame in memory. |
| `render_sidebar()` | Constructs the global persistent navigation pane: initializes default `st.session_state` keys (`selected_tags`, `period`, `show_events`, `log_scale`); renders tag multi-select, observation period radio, date range picker, event checkboxes, download CSV button, and CC BY-SA 4.0 licence expander; returns active filter dictionary. |

### Walk-Through: `src/export_dashboard_data.py`

| Component / Function | Purpose & Implementation Details |
|---|---|
| `EXPORT_SPECS` | Master dictionary mapping 27 output CSV names to their source relative paths (e.g., `reports/review2/ts/series_long.csv`) and their required column sets (`required_columns`). Serves as the formal data contract. |
| `ensure_dir(path)` | Utility creating destination directory (`dashboard/data/`) if non-existent. |
| `export_file(filename, spec, dest_dir)` | Core worker function: locates source file, validates that all required columns are present in the source DataFrame, subsets strictly to required columns, and exports a clean UTF-8 CSV into `dest_dir`. |
| `main()` | Iterates through all 27 entries in `EXPORT_SPECS`, prints row count, column count, and size in KB for each file, computes total bundle size, and enforces that the total payload remains under 50 MB (actual: 1.62 MB). |
